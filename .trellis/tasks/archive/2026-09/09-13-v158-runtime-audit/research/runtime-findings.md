### 触发链：已知与待证实分开

`debugLog.log.1:11192–11198`：13:17:39.344 正在终止脚本 → 39.490 停止监控 → 39.576 清缓存 → 39.579 进度 10/9999 → 42.656/43.186/43.669 仍有 UI 配置操作。随后 43.804 Windows 记录崩溃。13:18:47 配置重新加载与 UI 初始化证明新一轮应用启动。

- `app/farming_interface.py:730–732` 调 `self.my_script.terminate()`。
- `tasks/base/script_task_scheme.py:546–550`：先停止监控，再 `QThread.terminate()`，随后更换 Python 安全锁；没有等待原生推理安全点。
- `module/automation/automation.py:130–137` 只换输入/截图 RLock，无法修复被硬杀线程持有的 ONNX 原生状态。
- `module/ocr/ocr.py:16–28, 63` 使用 RapidOCR 的 ONNX Runtime 引擎；镜牢节点识别也使用 ONNX（须用 dump 定位具体执行分支）。

**强假设：** 停止时硬杀正在使用 ONNX 的 QThread，破坏原生执行生命周期，导致约 4.46 秒后访问冲突。时间关联与代码风险很强，但没有原生栈，不能断言这是唯一或已经完全证实的触发机制，也不能认定 ONNX 上游自身缺陷。

`except Exception` 不能兜住这类原生访问冲突。现有失败返回哨兵修复并不能解决原生崩溃。

## 事件卡住的代码原因及边界

- `tasks/battle/battle.py:514–528` 先点事件 SKIP 模板；未成功后调用 `resolve_event_page`，wait 时重置 chance、sleep、continue。
- `module/automation/automation.py:214,395` 的点击/查找默认阈值为 0.8。
- `tasks/event_page.py:134–143`：看到“判定成功/失败”后只查找含“继续”的文本；即使同帧 OCR 清楚识别出 `SKIP`，依然返回 wait。
- `.1:1604–1620`：SKIP 先 0.94，点击后变 0.78；同页有“本关卡中，鸿璐获得2强壮。”“判定成功”“SKIP”，无“继续”；后续重复稳定命中这个分支。第二次 `.1:12203–12220` 完全同构。
- `tasks/battle/battle.py:244,272–276` 没有事件结果专属期限，依赖整场 900+300*combat_count 秒；因此这不是无限循环，但约 15 分钟的无推进等待对无人值守仍明显有害。
- **不把所有 0.78 SKIP 当按钮可用证据**：`.3:16674–16687` 是只等待一次即出现“继续”的正常动画。0.78 也可能是禁用/动画态；需要原截图、视频或真实环境验证按钮状态，不能简单全局降阈值或认为 OCR 字符出现就总能点击。
- 本次没有日常选择首项反复点击 8 次失败、未确认结算、缺少 ONNX 地图节点等日志；不能挪用这些历史问题作为本次原因。

## 重启后主页滞留的代码原因

- `tasks/base/retry.py:218–229` 的超时会杀游戏并 restart；`restart_game():293–300` 包含 init_game 和 back_init_menu。`Battle.fight():272–276` 在此之后再次 back_init_menu 并返回 False，解释双次主页恢复。
- `tasks/mirror/mirror.py:114–122` 的 `_fight()` 丢弃底层 `battle.fight()` 返回值，调用点 `:377–394` 接着回到镜牢主循环。**False 在镜牢这里不等价单场战败**（上图返回地图也会 False），后续设计不能简单将 False 一律当终止，需明确区分“已在地图”和“恢复到了主页”。
- `.1:7440 起及 :7459–7460` 主页按钮模板仅约 0.25，OCR 可见“玻璃窗/驾驶席”等（例如 `:7469`）。`mirror.py:443` 只靠模板，不看已有主页 OCR，故未进入 road_to_mir。
- `mirror.py:220–222` 当 `main_loop_count>=50` 每轮开头强制 clam；`:483–488` 仅在尾部 count<75 时设 normal、<15 时设 aggressive。count 在 50–74 区间时 normal 会在下一轮开头被重置，模式升级存在局部失效；更主要的是本次直到停止仍剩 350，连宽范围尝试条件都未到。
- `utils/image_utils.py:212–244` clam 仅模板坐标裁剪，normal 才扩展搜索，aggressive 全屏。主页“文字可见但固定模板失败”的识别边界与上述长预算叠加，造成有画面仍空转。
- 截图底层 `module/automation/screenshot.py:237–243` 在窗口异常时直接 close_game/init_game；监控 `retry_monitor.py:99–107,138–151` 使用同一截图栈。在已有启动流程中截图会重入恢复；日志无线程 ID，不能仅凭它断言第二次一定来自哪个线程，但双入口与重复请求已实证。

## 待用户批准后实施与验证建议（非本轮改动）

1. **最高优先：原生崩溃/停止生命周期**。先获取现有 WER dump（需用户允许读取受保护文件或提供副本），确认崩溃线程、推理栈及 native 依赖版本。设计协作式取消，保留自然退出、暂停、停止、关闭窗体、重启任务完整生命周期；等待监控及业务线程安全结束，再释放/重用 OCR。不得只加 try/except 或换 Python 锁当原生修复。若无法协作取消原生挂死，再评估推理进程隔离，这属于架构选择需批准。
2. **事件状态机完整修复**。将结果动画与可推进页分清，保留正常动画保护；验证 OCR SKIP/继续的几何与上下文，加入独立 monotonic 无进展预算；覆盖判定成功/失败、SKIP 0.78/0.94、无按钮、误 OCR、正常 40 秒动画、反复无推进、服务器弹窗打断和恢复。无需用户在游戏里点按钮的方案才满足产品用途。
3. **统一恢复所有权**。截图返回“暂不可用”而非自行嵌套重启；重启控制器只允许一个 launch pending，监控在该期间不再触发 close/init。验证窗口短暂缺失、Steam 延迟、真实进程缺失、云同步弹窗和超时结束。
4. **恢复落点与状态传播**。为镜牢战斗返回显式结果或可靠落点分类，主页立即走有界重进入口，地图继续寻路，未知页才有限恢复；修正搜索模式被顶端重置以及大预算空转。测试 return-home / on-map / entry / battle / failed 五种分支，不单点修一个按钮。
5. **日志/真实验证**。后续经批准再加线程 ID、停止请求/退出确认、native 推理阶段、退出原因。自动化测试先验证上述状态迁移；隔离进程真实执行 OCR 中停止/再次启动的压力测试与 Windows 事件回查。不能在用户无人值守任务或现有游戏进度上未经同意压测。
